# Data manifest

Schema version 1 · quantities in integer grams of cooked food · timestamps stored in UTC, shown in Asia/Kolkata.

## What data exists in this repository

| Dataset | Status | Where | What it is |
|---|---|---|---|
| Demo seed | **Simulated** | `data/simulated/demo_seed.json` (copy served by the API in `services/api/proofplate/assets/`) | 27 diner tokens, 9 services, generated from seed `20261011`. Five tokens are hand-scripted for the walkthrough. Hash and counts in `data/simulated/MANIFEST.json`. |
| Evaluation output | **Simulated** | `evaluation/outputs/evaluation.json` | Policy comparison over nine simulated scenarios and eight seeds, plus a frontier sweep. |
| Pilot measurements | **None collected** | — | The pilot workspace starts empty. |

No real diner, kitchen or weighing is represented anywhere in this repository.

## Provenance labels carried by every record

| `origin` | Meaning | Trains the live pilot model? |
|---|---|---|
| `measured` | Entered by a signed-in operator in the pilot workspace, as a scale reading (`weighed`) or a calibrated scoop estimate (`scoop_estimate`) | yes |
| `simulated` | Generated, or typed into the public demo sandbox (`entry: demo_entry`) | only the demo's own model |
| `imported` | Loaded from a file, with `measurement_status` `measured` or `synthetic` as declared in the import manifest | only if declared `measured` |

"Measured" is a declared status. The application does not independently verify that a weighing happened.

Rules enforced in code (`service.py`, `transfer.py`) and tests (`tests/test_api.py`):

- Simulated and synthetic records never enter the pilot model or a pilot result.
- An import cannot promote its rows to `measured` origin. Imports made in the demo are always stored as synthetic.
- Every evidence figure is reported per source group with its date range, sample count and return coverage.
- A missing return is missing, not zero waste.
- Demo reset clears only the browser's own sandbox.

## Photos

Photos used for the leftover estimate are analysed in the browser and are never sent to the server. What is saved with the return event is numeric: the estimated grams, its standard deviation, and a `photo_detail` record (the food's share of the plate before and after, the reference grams, the exponent used, and whether an outline was corrected by hand). On the device, the browser keeps a small thumbnail and the share for each open plate's before photo, and per-food calibration points, in local storage.

The demo's before/after pair in `apps/web/public/samples/photos/` is generated by `scripts/make_sample_photos.py` and labelled as such in its manifest.

## Regenerating the simulated data

```
python scripts/make_demo_seed.py          # demo seed + manifest (deterministic)
python -m evaluation.run_evaluation       # policy comparison
python -m evaluation.run_frontier         # waste-versus-availability sweep
```

## Import manifests

Each import stores a manifest record: source name and URL, license, collection method, what it measures, measured or synthetic, file SHA-256, row count, operator and time. See `data/templates/README.md`.

## External datasets

None are used. No public dataset was found that records repeated diner identity, offered portions, seconds, edible leftovers and satisfaction together. Food-image datasets such as Nutrition5k hold dish scans with mass and nutrition labels; they do not contain appetite or waste outcomes and are not used here.

## Retention and deletion

- Pilot records are kept in the DynamoDB table until deleted. The table is retained on stack teardown; delete it explicitly to remove data.
- Deleting a diner token removes that token's events, idempotency anchors and plate counters. Models are rebuilt by replay, so later estimates exclude them. Service-level kitchen totals typed in by staff are not per-diner and are kept.
- Application logs hold request id, route, status and duration only. They do not contain diner payloads.
